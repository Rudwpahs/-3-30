# KAIST IP 자기소개서 작성기 설계

## 1. 목표

기존 `Rudwpahs/-3-30` 저장소의 중국어 학습 앱을 전부 교체하고, KAIST IP영재기업인교육원 지원용 자기소개서 작성기를 새로 구축한다.

이 서비스의 핵심은 다음 세 가지다.

1. 지원자가 5개 자기소개서 문항을 안정적으로 작성하고 브라우저에 자동 저장한다.
2. 검증된 개인 소재를 `Verified 소재 DB`에서 찾아 문항에 활용하고, 과장·위험표현을 실시간으로 경고한다.
3. 평소 초안은 로컬에만 보관하고, 사용자가 명시적으로 `GPT에게 검토 요청`을 눌렀을 때만 선택한 문항을 서버에 전송해 이후 ChatGPT가 해당 초안을 확인할 수 있게 한다.

## 2. 배포 전략

사용자가 선택한 B안으로 진행한다.

- **실제 서비스 런타임/배포:** Floot 풀스택 앱
- **소스 보관:** GitHub `Rudwpahs/-3-30`
- **개발 브랜치:** `work/kaist-ip-writer`
- **최종 반영:** 기능 검증 후 `main`
- **GitHub 기존 앱:** 최종 반영 시 새 사이트 소스로 완전히 교체

Floot는 프론트엔드와 서버 엔드포인트, 데이터베이스를 함께 운영한다. GitHub에는 재현 가능한 소스와 문서, 테스트를 유지한다. Floot 전용 파일 구조와 GitHub Vite 구조가 완전히 동일하지 않을 수 있으므로, GitHub에는 동일한 기능과 데이터 모델을 재현할 수 있는 소스와 설계 문서를 유지한다.

## 3. 자기소개서 문항

2027년도 18기 지원 흐름을 기준으로 5개 문항을 제공한다. 각 문항은 공백 포함 1,000자 제한을 적용한다.

1. 자신이 좋아하는 일 또는 잘하는 일과 그 이유
2. 그 분야와 관련해 본받고 싶은 Role Model과 이유
3. KAIST IP영재기업인교육원 지원동기, 향후 진로계획, 본인을 선발해야 하는 이유
4. 지금까지 가장 소중한 지적 성취 경험과 그 경험이 본인에게 미친 영향
5. 학업 외 가장 소중한 활동 경험과 그 활동이 본인에게 미친 영향

화면에는 문항 제목, 안내문, 현재 글자 수, 제한 1,000자를 표시한다. 정확한 공식 문구는 구현 전에 KAIST IP-CEO 공식 모집자료와 다시 대조하고, 의미를 바꾸는 임의 축약은 하지 않는다.

## 4. UI: Editorial Glass

기존 대화에서 정한 `Editorial Glass` 디자인을 유지한다.

### 4.1 기본 인상

- 흰색/아이보리 기반 편집지 느낌
- 얇은 경계선과 반투명 유리 패널
- 큰 에디토리얼 타이포그래피
- 과한 그라데이션·게임형 UI 배제
- 작성 영역은 읽기와 집중을 우선
- 데스크톱과 모바일 모두 동일 기능 제공

### 4.2 화면 구조

데스크톱:

- 좌측: 5개 문항 내비게이션, 진행률, 자동저장 상태
- 중앙: 선택한 문항 편집기
- 우측: Verified 소재 DB, 위험표현 경고, 맞춤법 검사, 검토 요청

모바일:

- 상단: 문항 탭
- 중앙: 편집기
- 하단 시트: 소재/경고/맞춤법/검토 기능

## 5. localStorage 자동저장

자기소개서 본문은 기본적으로 서버로 전송하지 않는다.

브라우저의 `localStorage`에 다음 정보를 저장한다.

- 5개 문항 초안
- 마지막 선택 문항
- 소재 DB 필터 상태
- 위험표현 경고 닫기 상태
- 외부 전송 동의 상태
- 검토 채널 식별용 브라우저 UUID

초안은 입력 후 짧은 debounce를 두고 자동 저장한다. 새로고침이나 재접속 시 즉시 복원한다.

명확한 `초기화` 버튼을 제공하며, 초기화 전 확인 모달을 띄운다.

## 6. Verified 소재 DB

Verified 소재는 별도 구조화 데이터로 관리한다. 각 항목은 다음 필드를 가진다.

```ts
type EvidenceStatus = 'VERIFIED' | 'TIME_BOUND' | 'CONFLICT' | 'SELF_REPORT'

type Material = {
  id: string
  title: string
  summary: string
  period: string
  tags: string[]
  status: EvidenceStatus
  sourceLabel: string
  sourceNote: string
  suggestedQuestions: number[]
}
```

초기 데이터에는 대화에서 확인된 자료 중 출처를 명확히 연결할 수 있는 것만 넣는다.

예시 범주:

- 머신러닝/MediaPipe 자세 분석 기반 AI 요가 프로그램
- 전동킥보드 사고 데이터 수집·시각화·예측 및 시뮬레이터/웹사이트 제작
- 포트폴리오 웹 개발 프로젝트
- 영재원 여름캠프의 Design Thinking, AI 학습 관련 활동

각 항목은 `Verified`, `Time-bound`, `Conflict`, `Self-report` 상태를 시각적으로 구분한다. 소재를 클릭하면 편집기에 자동으로 문장을 생성하지 않고, 핵심 사실 메모만 삽입하거나 클립보드용 메모로 제공한다. 자기소개서의 최종 문장은 사용자가 작성하도록 유지한다.

## 7. 위험표현 경고

위험표현 검사는 브라우저에서 실시간으로 동작한다. 서버 전송이 필요 없다.

초기 규칙 범주:

- 절대적·과장 표현: `최초`, `완벽`, `무조건`, `세계 최고`, `유일`, `100%` 등
- 검증이 필요한 성과 수치
- 타인이 작성한 것처럼 보일 수 있는 과도하게 성인적인 문체
- 소재 DB와 충돌하는 연도·기관·성과
- 자신이 직접 수행한 것과 팀 활동의 경계가 불분명한 표현
- 타인의 아이디어/성과를 본인의 단독 성과처럼 표현할 위험

경고는 `오류`가 아니라 검토 신호로 보여준다. 자동 삭제하거나 강제로 수정하지 않는다.

## 8. 맞춤법 검사

기존 Python `py-hanspell` 기능은 Floot에서 직접 실행하지 않는다. 사용자 경험은 유지하되 서버 런타임에 맞게 TypeScript 기반 어댑터로 이식한다.

### 8.1 사용자 계약

- 맞춤법 검사는 사용자가 버튼을 눌렀을 때만 실행
- `외부 전송 동의`가 꺼져 있으면 호출 자체를 차단
- 호출 직전 어떤 텍스트가 서버/외부 처리기로 전송되는지 안내
- 전체 초안이 아니라 현재 선택 문항만 전송
- 교정 결과는 원문/제안문을 비교해 보여주고 사용자가 개별 또는 전체 적용
- 자동으로 본문을 덮어쓰지 않음

### 8.2 서버 계약

```ts
type SpellcheckRequest = {
  text: string
  consent: true
}

type SpellcheckSuggestion = {
  original: string
  replacement: string
  reason?: string
}

type SpellcheckResponse = {
  correctedText: string
  suggestions: SpellcheckSuggestion[]
  provider: string
}
```

긴 문장은 500자 안팎의 안전한 단위로 분할한 뒤 합친다. 이는 기존 `py-hanspell` 사용 시 긴 문장을 나누어 처리하던 사용 경험을 유지하기 위한 것이다.

Floot 런타임에서 사용할 수 있는 교정 제공자는 구현 단계에서 실제 지원 여부를 확인한 뒤 선택한다. 우선순위는 다음과 같다.

1. Floot에서 안정적으로 호출 가능한 서버측 한국어 교정 기능
2. 외부 한국어 맞춤법 API

어떤 경우에도 동의 없이 외부 호출하지 않는다. 제공자가 실패하면 원문을 변경하지 않고 `맞춤법 서비스를 사용할 수 없음` 오류를 표시한다.

## 9. GPT 검토 요청: local-first + 명시적 서버 공유

평소 작성 내용은 `localStorage`에만 존재한다.

사용자가 각 문항의 `GPT에게 검토 요청` 버튼을 누르면 다음 과정을 거친다.

1. 현재 문항 번호와 본문을 보여주는 확인 모달
2. `이 문항을 서버에 저장하고 ChatGPT 검토용으로 공유합니다` 문구 표시
3. 사용자가 확인
4. 서버 DB에 해당 문항만 저장
5. 성공 메시지: `검토 요청 완료 — ChatGPT에서 “방금 쓴 3번 봐줘”라고 말하세요.`

서버에는 명시적으로 공유한 버전만 저장한다. localStorage 자동저장과 서버 저장은 별개다.

## 10. 검토 요청 데이터 모델

Floot 관리형 Postgres에 다음 개념을 저장한다.

```ts
type ReviewRequest = {
  id: string
  browserId: string
  questionId: 1 | 2 | 3 | 4 | 5
  content: string
  charCount: number
  createdAt: string
  version: number
  status: 'pending' | 'reviewed'
}
```

서버는 공개 읽기 API를 제공하지 않는다. 브라우저는 `POST /_api/review-requests`만 사용한다. 이후 ChatGPT는 사용자의 연결된 Floot 프로젝트 도구를 통해 데이터베이스의 최신 검토 요청을 조회할 수 있다.

향후 사이트를 다른 사람이 사용하게 되는 경우를 대비해 `browserId`와 생성시각을 저장하며, UI에는 선택적으로 검토 코드도 표시할 수 있다. 현재 제품은 단일 사용자 개인 작성 도구를 기본 전제로 한다.

## 11. 버전 관리

같은 문항에서 검토 요청을 여러 번 보내면 버전 번호를 올린다.

예:

- 3번 v1
- 3번 v2
- 3번 v3

ChatGPT가 이후 `지난 버전과 비교해줘`라는 요청을 받으면 같은 문항의 두 버전을 비교할 수 있는 구조로 저장한다.

## 12. 개인정보/외부 전송 원칙

- 자동저장 초안: 브라우저 로컬 전용
- 위험표현 검사: 브라우저 로컬 전용
- Verified 소재 검색: 브라우저 로컬 전용
- 맞춤법 검사: 사용자 명시 동의 후 현재 문항만 서버/교정 제공자에 전송
- GPT 검토 요청: 사용자가 확인한 현재 문항만 Floot DB에 저장
- 공개 읽기 API 금지
- 서버 로그에 자기소개서 본문을 의도적으로 출력하지 않음

## 13. 주요 컴포넌트

프론트엔드 책임을 다음처럼 분리한다.

- `EssayWorkspace`: 전체 레이아웃과 현재 문항
- `QuestionNavigator`: 5문항 이동/진행률
- `EssayEditor`: textarea, 글자 수, 저장 상태
- `MaterialPanel`: Verified 소재 검색/필터
- `RiskPanel`: 위험표현 탐지 결과
- `SpellcheckPanel`: 동의/검사/제안 적용
- `ReviewSharePanel`: 서버 공유 확인과 버전 표시
- `useLocalDrafts`: localStorage 저장·복원
- `riskRules`: 브라우저 규칙 기반 검사
- `materials`: 검증 소재 데이터

서버 책임:

- `POST /_api/review-requests`: 명시적으로 공유한 검토 요청 저장
- `POST /_api/spellcheck`: 동의 검증 후 맞춤법 처리

## 14. 오류 처리

- localStorage 접근 실패: 화면 상단에 `자동저장을 사용할 수 없음` 표시
- 1,000자 초과: 입력 자체를 강제로 자르지 않고 초과 상태를 빨간색으로 표시
- 맞춤법 서버 실패: 본문 유지, 재시도 버튼 표시
- 검토 요청 저장 실패: 로컬 초안 유지, 서버 저장 실패 메시지 표시
- 네트워크 중단: 어떤 자동 서버 동기화도 수행하지 않으므로 작성은 계속 가능

## 16. GitHub 교체 원칙

`work/kaist-ip-writer`에서 새 프로젝트를 완성하고 검증한 후 `main`에 반영한다.

최종 `main`에는 기존 중국어 학습용 파일과 의존성을 남기지 않는다. 기존 Git 이력은 보존되므로 과거 커밋으로 복구 가능하다.

최종 저장소에는 최소한 다음이 포함된다.

- 새 사이트 소스
- 테스트
- README
- `docs/superpowers/specs/` 설계 문서
- `docs/superpowers/plans/` 구현 계획
- 배포/재현 방법

기존 GitHub Pages 자동배포 워크플로는 Floot를 production으로 사용하는 설계와 충돌하므로 최종 단계에서 제거하거나 문서용 빌드 검증 워크플로로 교체한다.
